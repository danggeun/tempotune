# Go practice — 제품화 로드맵 v2 (2026-09-05)

> 목표: "동작하는 프로토타입"에서 "개발자 사이드 프로젝트로 내놓을 수 있는 제품"으로.
> 전제: 배포 압박 없음, 리팩토링 허용, 기능/UX 다운그레이드 없음, 현재 디자인 언어 유지.

## 0. 결정 사항 (2026-09-05 확정)

| 항목 | 결정 | 이유 |
|---|---|---|
| 스택 | 웹 + **TypeScript** + Vite + Capacitor(Android) | UI/UX 자산이 HTML/CSS에 있음. TS는 AI가 짜는 코드의 안전망 |
| AI 감지 | YAMNet 제거 → **신호처리 기반** 연주 감지 | 오프라인, 배터리, 첼로 저음, 조용한 실패 제거 |
| 플랫폼 | Android 앱 우선, iOS는 PWA(Safari 동작 보장) | Xcode/개발자 계정 불필요 |
| 리팩토링 | 허용 (Flutter 재작성 계획 철회) | 사용 목적이 본인+주변으로 바뀜 |

## 1. 현재 상태 진단 요약

**잘 된 것**: YIN + FFT 교차검증, lookahead 메트로놈 스케줄러, IndexedDB, 이벤트 위임, 순수 함수 분리 + 테스트 17개, 절제된 디자인 언어(검정 카드/초록 밴드/빨강 단일 액센트/모노 숫자/아이콘 없는 텍스트 버튼).

**벽이 되는 것**:
1. `main.js` 1,054줄 단일 파일, 전역 상태 `S`/`A`, 오디오 로직과 DOM 조작이 한 함수에 섞임
2. 오디오 분석(YIN O(N²))이 메인 스레드, `ScriptProcessorNode` 폐기 예정 API
3. YIN 신뢰도(d′)를 버리고 휴리스틱(lockFrames/rmsWeak/octaveJump)으로 보완
4. `hzMin: 80` — 첼로 C현(65 Hz), 베이스(41 Hz) 연주 감지 누락 가능 (확인 필요)
5. YAMNet CDN 런타임 로드, 실패해도 "준비됨" 표시, 오프라인 불가
6. UI 상태 전이를 `maxHeight`/`offsetHeight` 수동 조작으로 처리 (커밋 6개+ 소모)
7. 편집기 파일명 수정이 IndexedDB에 저장 안 됨
8. PWA 아님(manifest/SW 없음), 폰트 CDN 의존
9. `<a download>`가 Android WebView에서 동작하는지 미확인 (확인 필요)
10. 테스트가 순수 함수에만 있고 상태/타이밍 로직엔 없음

## 2. 디자인 언어 (지킬 것)

이번 개선에서 **바꾸지 않는** 것을 먼저 고정한다.

- 팔레트: 배경 회백/검정, 텍스트 흑/백, 액센트는 빨강(`--red`) 하나 + 상태색 초록(in-tune)/앰버(북마크)
- 타이포: Cormorant Garamond 이탤릭 로고, Noto Sans KR 본문, DM Mono 숫자
- 아이콘 최소화, 텍스트 버튼, 얇은 1.5px 테두리, 14px 라운드
- 튜너 카드는 항상 검정(다크/라이트 무관), 히스토리는 아래→위로 흐름
- 한국어 음이름(도~시), 이명동음 병기
- 메뉴/설정/편집은 풀스크린 페이지로 전환

UI 변경은 "이 언어 안에서 디테일을 올리는 것"만 허용: 터치 타겟, 상태 피드백, 전이 품질, 정보 밀도.

## 3. 목표 아키텍처

```
www/src/
  core/        순수 알고리즘 (DOM/Web Audio 없음, 100% 테스트)
    pitch/     yin.ts, confidence.ts, fft.ts, harmonics.ts, noteMath.ts
    playing/   playingDetector.ts   ← YAMNet 대체
    metro/     scheduler.ts (시간 계산만)
    wav.ts, format.ts
  audio/       Web Audio 어댑터
    capture.worklet.ts   AudioWorklet: 마이크 → 링버퍼 → Worker 전송
    analysis.worker.ts   Worker: YIN/FFT/감지 실행 → 결과 메시지
    engine.ts            AudioContext 생명주기, 마이크 열기/닫기, 인터럽트 복구
    metronome.ts, refTone.ts, recorder.ts
  state/       단일 스토어 (상태 + 구독). UI는 여기만 본다
  ui/          카드 단위 모듈 (tuner, metro, menu, settings, editor, recList)
  platform/    capacitor.ts / web.ts (권한, 파일 저장, 상태바, wake lock)
  main.ts      조립만
```

원칙: `core/`는 브라우저 API를 import하지 않는다. `ui/`는 `audio/`를 직접 호출하지 않고 `state/`를 통한다. 이 두 규칙이 "기능 추가 시 어디가 깨질지 모르는" 비용을 없앤다.

## 4. 단계별 계획

각 단계: 세부 계획 제시 → 승인 → 브랜치에서 구현 → 자동 검증 → **실기기 테스트(사용자)** → 머지.

### Phase 0 — 기준선 고정 (다운그레이드 방지 장치)
- 왜: "모든 면에서 업그레이드"를 검증하려면 지금 상태를 정확히 기록해야 한다.
- 할 일
  - Playwright 스크린샷 기준선 (라이트/다크 × 메인/메트로/메뉴/설정/편집) → 이후 픽셀 diff로 UI 회귀 검출
  - 기능 체크리스트 문서화 (사용자 관점 시나리오 ~30개)
  - 실기기 성능 기준: 중급 Android에서 튜너 프레임 시간, 메트로 지터 측정 스크립트
  - 프로젝트 문서 동기화 (Technical/Contents/Code 갱신 또는 폐기)
- 완료 기준: 체크리스트 + 스크린샷이 리포에 커밋됨

### Phase 1 — TypeScript 전환 + 구조 분리 (동작 변경 0)
- 왜: 이후 모든 변경의 안전망. 기능은 하나도 안 바꾸고 "같은 동작을 다른 구조로".
- 할 일
  - `tsconfig` strict, Vite TS 빌드
  - `S`/`A` 전역 → `state/` 스토어로 이동, UI 모듈이 구독
  - `main.js` → `ui/*` 카드별 분리, 이벤트 바인딩 모듈화
  - 메트로 접기/펼치기 `maxHeight` 해킹 → CSS `grid-template-rows: 0fr/1fr` 전이로 교체 (JS 측정 제거)
  - 편집기 파일명 IndexedDB 저장 (버그 수정, 이 단계에서 유일한 동작 변경)
- 완료 기준: 스크린샷 diff 0, 체크리스트 전부 통과, `tsc --noEmit` 에러 0

### Phase 2 — 오디오 코어 재설계 (제품급 튜너)
- 왜: 튜너 품질과 폰 성능이 여기서 결정된다. 가장 큰 투자, 가장 큰 이득.
- 할 일
  - AudioWorklet 캡처 → SharedArrayBuffer 또는 postMessage 링버퍼 → Analysis Worker
  - Worker에서 YIN 실행 (매 프레임, 스킵 없음) + **d′ 신뢰도 반환**
  - 신뢰도 기반 락/스무딩: 휴리스틱 3종 제거, 신뢰도 가중 중앙값 필터로 교체
  - 자체 FFT(Worker) + 하모닉 구조 분석 → `AnalyserNode` 제거
  - **연주 감지기**(YAMNet 대체): 신뢰도·하모닉 수·스펙트럼 평탄도·지속 시간 조합. 첼로/베이스 저음 커버(`hzMin` 40 Hz)
  - 튜너 창 크기 재검토 (저음 정확도 vs 반응 속도, 악기별 프리셋 가능성)
  - **테스트 자산**: 합성 신호 + 사용자가 폰으로 녹음한 실제 개방현/스케일 WAV로 오프라인 정확도 회귀 테스트 (cents 오차, 락 지연, 오검출률 수치화)
- 사용자 참여: 바이올린/첼로 개방현·스케일·비브라토 녹음 파일 제공
- 완료 기준: 실녹음 세트에서 기존 대비 cents 오차·오검출률 개선 수치 확인, 중급 Android에서 메인 스레드 프레임 시간 개선

### Phase 3 — 메트로놈 / 기준음 강화
- 왜: 이미 정석 구조. 손댈 곳은 백그라운드 안정성과 음질.
- 할 일
  - 스케줄러 타이머를 Worker로 이동 (화면 꺼짐/백그라운드 시 `setTimeout` 스로틀링 회피)
  - 클릭음: 오실레이터 → 짧은 샘플 또는 정형 합성으로 강박/약박/세분 구분 명확화
  - 오디오 컨텍스트 단일화 (마이크/메트로 컨텍스트 전환 로직 제거)
  - 기준음: 배음 포함 파형으로 튜닝 시 듣기 쉽게 (확인 필요: 사용자 취향)
  - 기능 추가(탭 템포 등)는 사용자 요청 시에만
- 완료 기준: 30분 백그라운드 재생 지터 측정, 인터럽트(전화/알림) 후 복구

### Phase 4 — 녹음 / 편집기
- 왜: 실사용에서 가장 자주 쓰는 사후 기능. 편집기에 파형이 없는 게 가장 큰 UX 공백.
- 할 일
  - 파형 렌더링 (디자인 언어 안에서: 모노톤, A-B 구간만 색)
  - Android 파일 저장: `<a download>` → Capacitor Filesystem + Share (확인 필요)
  - 저장 실패/용량 부족 표면화, 녹음 중 인터럽트 처리
  - 녹음 목록 상태(이름/북마크/A-B) 영속화
- 완료 기준: 녹음→편집→저장→공유가 Android에서 끝까지 동작

### Phase 5 — 앱 완결성
- 왜: "가끔 이상하게 동작"이 제품과 프로토타입의 차이.
- 할 일
  - 오프라인: 폰트 번들, manifest, Service Worker (PWA 실제화)
  - 생명주기: 화면 꺼짐/앱 전환/전화 수신 시 오디오 상태 복구 매트릭스
  - 조용한 실패 금지: 모든 catch에 사용자 피드백 또는 로그
  - 권한 흐름: 거부/영구 거부 각각의 안내
  - 성능 프로파일: 배터리, 메모리(장시간 녹음), 저사양 기기
- 완료 기준: 비행기 모드에서 전 기능 동작, 생명시기 매트릭스 전부 통과

### Phase 6 — UI/UX 디테일 (디자인 언어 유지)
- 왜: 지금 언어를 유지하면서 "만져보면 다르다"를 만드는 단계.
- Phase 4 리뷰에서 넘어온 편집기/목록 격차 (우선순위순): 파형 확대(A-B 설정 시 더블탭 → 구간 ±2 s, 상단 미니맵) · 반복 프리롤(꺼짐→켜짐→켜짐·1 s) · 북마크 라벨(길게 눌러 한 단어) · 목록 정보밀도(북마크 n · A-B · n일 후 삭제) · 목록에서 이름 바로 수정 · 속도 프리셋(0.5/0.7/0.85/1.0, 녹음별 기억) · 재생 버튼 ■→❚❚
- 할 일

  - 햅틱(메트로 강박, 락 시점) — 확인 필요: 배터리/취향
  - 태블릿 2컬럼 레이아웃 재검토
  - 첫 실행 온보딩 최소화 (마이크 권한 1회 안내만)
- 완료 기준: 스크린샷 기준선과 비교해 의도한 변경만 존재

## 6. 작업 방식

- 사용자는 JS/TS를 모른다는 전제. 모든 변경은 "무엇을/왜/영향 범위" + 개념 설명 동반.
- 코드 변경은 브랜치 + PR 단위. 각 PR은 자동 검증(테스트/스크린샷) 통과 후 사용자 실기기 테스트.
- 진행 상황은 이 문서의 체크박스로 추적. 결정 변경 시 §0 표에 기록.
